## What it is, in plain terms
A new EKS cluster runs pods, but it can't yet do three things almost every real cluster needs:

- **Create load balancers from Ingress objects.** An *Ingress* is a Kubernetes rule that says "send requests for this hostname to that service". The **AWS Load Balancer Controller** watches Ingresses and builds an **Application Load Balancer** (ALB, an HTTP-aware AWS load balancer) for them.
- **Report resource usage.** **metrics-server** collects CPU and memory per pod and node. `kubectl top` and the **HorizontalPodAutoscaler** (which adds or removes pods by load) read from it.
- **Publish DNS names.** **external-dns** writes **Route 53** (AWS's DNS service) records for the hostnames in your Ingresses, so `app.example.com` points at the ALB.

These are installed with **Helm**, a package manager for Kubernetes. A *chart* is the package; a *values file* is the settings you give it. **kind** (Kubernetes in Docker) runs a whole cluster as a Docker container, which gives a free, disposable place to test charts.

## How it works
`charts.env` holds each chart's repository and an exact version. Both scripts read it, so there is one place to bump:

```bash
LBC_CHART_VERSION=1.13.0
METRICS_SERVER_CHART_VERSION=3.12.2
EXTERNAL_DNS_CHART_VERSION=1.16.1
```

Each add-on has a production-style `values.yaml` (two replicas, a PodDisruptionBudget, resource requests, non-root, read-only filesystem, `system-cluster-critical` priority). A second file under `kind/` overrides only what kind forces. The smoke test layers them, later file winning:

```bash
helm upgrade --install "$1" "$2" --version "$3" -f "$HERE/$4/values.yaml" -f "$HERE/kind/$4.yaml" --wait
```

The `serviceAccount.name` values (`aws-load-balancer-controller`, `external-dns`) are the names the Pod Identity associations from `modules/eks-pod-identity` must use. There is no role annotation: with Pod Identity the association grants the role, not the ServiceAccount.

`smoke-test.sh` creates the cluster, installs the three charts, waits for each Deployment, then polls `kubectl top nodes` until metrics-server answers. A `trap` deletes the cluster even on failure (`KEEP_CLUSTER=1` keeps it).

## Why it's built this way
- **Pinned versions.** An unpinned chart upgrades silently. Pinning makes every cluster change a commit.
- **Empty per-cluster defaults.** `clusterName`, `vpcId` and `txtOwnerId` default to empty, so a forgotten `--set` fails at install time instead of managing the wrong cluster.
- **external-dns `upsert-only`.** It creates and updates records but never deletes them. A bad manifest can't take a hostname offline; switch to `sync` when you trust it.
- **kind uses fake AWS.** The load balancer controller runs with a made-up VPC ID and test credentials; external-dns uses its in-memory provider. That tests the chart and the pods, not AWS behaviour. The README says so.
- **Not wired into `scripts/check.sh`.** The agent sandbox has no Docker, and CI shouldn't depend on downloading charts. `platform/tests/lint.sh` is the offline part; the smoke test is run by hand.

## Interview questions
<details><summary>1. Why pin Helm chart versions?</summary>

A chart's templates and defaults change between versions. Without a pin, `helm upgrade` on a different day can change Deployments, RBAC or CRDs with no diff in your repo. A pinned version makes the cluster state reproducible and upgrades reviewable.

</details>

<details><summary>2. What does the AWS Load Balancer Controller do, and why does it need IAM permissions?</summary>

It reconciles Kubernetes Ingress and Service objects into ALBs and NLBs, target groups, listeners and security groups. Those are AWS API calls, so the controller's pod needs a role whose policy allows them, ideally scoped by tag so it can only touch resources it created.

</details>

<details><summary>3. Why test with kind when it can't create real load balancers?</summary>

It is free and disposable, and it catches the common failures: a values file the chart rejects, a pod that crash-loops, a webhook that never becomes ready. What it can't catch is IAM or AWS-side behaviour, which needs a real account.

</details>
