## What it is, in plain terms
**ECR** (Elastic Container Registry) is AWS's private store for container images. You build an image, tag it (`api:3f9c1e2`) and `docker push` it to a **repository**, which is the folder in the registry that holds all versions of one image. Kubernetes nodes in EKS later pull from there. Think of it as a private Docker Hub inside your account, with IAM deciding who may push and pull.

Four ideas matter here:

- **Tag mutability.** A tag is a movable label on an image, like a git branch. In a *mutable* repository, pushing `latest` again silently moves the label. In an *immutable* one the push is rejected, so a tag always means the same bytes.
- **Scan on push.** ECR checks each image's packages against a database of known vulnerabilities (CVEs) the moment it is pushed.
- **Encryption at rest with KMS.** Images are encrypted by default with a key AWS owns. A **customer-managed KMS key** (see [2026-11-17](2026-11-17.md)) is one you control, so access is checked twice (repository permission and key permission) and every key use appears in CloudTrail, the audit log.
- **Lifecycle policy.** Rules that delete old images automatically. Without them every CI build adds storage cost forever.

## How it works
One module call takes a map of repositories and a key ARN (Amazon Resource Name, a resource's unique ID):

```hcl
repositories = {
  api    = {}                       # keeps the last 30 images
  worker = { keep_last_images = 10 }
}
```

`for_each` over that map creates each repository with the settings that have no switch:

```hcl
image_tag_mutability = "IMMUTABLE"
image_scanning_configuration { scan_on_push = true }
encryption_configuration { encryption_type = "KMS", kms_key = var.kms_key_arn }
```

Names come from the `labels` module (`platform-dev-api`), so they follow [ADR 0002](../adr/0002-naming-and-tagging.md). The lifecycle policy is a JSON document built with `jsonencode`:

```hcl
rules = [
  { rulePriority = 1, selection = { tagStatus = "untagged", countType = "sinceImagePushed", countUnit = "days", countNumber = var.untagged_expiry_days }, action = { type = "expire" } },
  { rulePriority = 2, selection = { tagStatus = "any", countType = "imageCountMoreThan", countNumber = each.value.keep_last_images }, action = { type = "expire" } },
]
```

Rule 1 removes untagged images (build leftovers) after a week. Rule 2 keeps the newest N images of any kind and expires the rest. ECR evaluates rules in priority order.

## Why it's built this way
- **Safety settings are not variables.** A variable that can turn off scanning or immutability will, someday, be turned off. If a team genuinely needs a mutable repository, that is a conversation and a code change, not a flag.
- **A key is required, not optional.** The AWS-owned default key costs nothing but cannot be audited or restricted. A customer-managed key costs about $1 a month and gives a second gate. The module takes the key ARN as an input instead of creating the key, so one key can serve several repositories and the key's policy stays in the `kms` module.
- **`kms_key_arn` rejects aliases.** ECR needs the key ARN. An alias would pass `plan` and then fail at `apply`, so a `validation` block turns that into an early, readable error.
- **`force_delete` defaults to false**, so destroying a repository that still holds images fails instead of deleting them. Only the drill stack sets it, because destroy must always finish.
- **Left out on purpose:** repository policies for cross-account pulls, and replication. Nothing needs them yet.

## How it's tested
- **Unit tests (mock provider, plan):** every repository is immutable, scanned and uses the key; per-repository `keep_last_images` reaches the right rule; `untagged_expiry_days` is configurable; five `expect_failures` runs prove the validations (empty map, bad key name, count out of range, alias instead of ARN, expiry out of range).
- **Moto test (apply):** first applies `modules/kms` to make a real key, then the registry on top of it, and reads back what Moto stored: settings, key, the stored lifecycle policy and outputs. Moto stores the lifecycle policy but never runs it, and never scans, so those two behaviours are covered as configuration only.
- `live/stacks/m3` has its own small unit test for names, live tags and region validation.

## Interview questions

<details><summary>1. Why make image tags immutable?</summary>

So a tag always refers to the same image. With mutable tags a restarted node can pull different code than the one tested or rolled out, and rollbacks become unreliable. CI should push a unique tag such as the git SHA.

</details>

<details><summary>2. What does scan-on-push protect you from, and what does it not?</summary>

It reports known vulnerabilities in the image's OS and language packages at push time. It does not block a push or a deployment by itself, does not find unknown flaws, and an image can become vulnerable later when a new CVE is published, so scanning must also be continuous or re-run.

</details>

<details><summary>3. Why keep both an "expire untagged" rule and a "keep last N" rule?</summary>

They solve different problems. Untagged images are leftovers nobody can reference, so they go quickly. The count rule bounds total storage while always leaving recent tagged images available as rollback targets.

</details>
