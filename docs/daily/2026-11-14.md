<details><summary>2. You rename <code>project</code> from <code>platform</code> to <code>acme</code>. What does Terraform do to resources whose names came from <code>labels</code>, and why is today's log group a good example of the pain? (from <a href="2026-11-09.md">2026-11-09</a>)</summary>

Names are inputs, and many AWS resources cannot be renamed, so Terraform destroys and recreates them. A log group named `/aws/vpc/flow-logs/platform-dev-flow-logs` would be deleted along with its history, and the KMS alias and role names change too.

## What it is, in plain terms
A **flow log** is a record of network connections: for each flow it stores source and destination address and port, protocol, bytes, and whether the traffic was accepted or rejected. It never holds packet contents. You use it to answer "who talked to whom?" and "what is my security group blocking?" after the fact.

**CloudWatch Logs** is AWS's log storage and search service. A **log group** is a named bucket of logs with its own retention period. **KMS** (Key Management Service) holds encryption keys, and a **customer-managed key** is one you own and write the policy for. An **IAM role** is an identity that a service can temporarily *assume* to act with a fixed set of permissions: here, the flow logs service assumes one to write into the log group.

## How it works
The key policy is the subtle part. CloudWatch Logs needs to use the key, but only for this log group:

```hcl
Condition = {
  ArnEquals = { "kms:EncryptionContext:aws:logs:arn" = local.log_group_arn }
}
```

An **encryption context** is extra labelled data that KMS checks on every use. CloudWatch Logs puts the log group's ARN in it, so the key cannot be used for any other group. The log group ARN is built from its documented format instead of read from the resource, because the key policy names the log group and the log group names the key: reading the ARN would make a dependency cycle.

The role has a trust policy and a permissions policy. Trust says who may assume it (`vpc-flow-logs.amazonaws.com`, and only for this account, which prevents the "confused deputy" problem where another account tricks a service into using your role). Permissions are three `logs:` actions on the one log group, never `Resource: "*"`:

```hcl
Resource = [local.log_group_arn, "${local.log_group_arn}:*"]
```

`retention_in_days` is validated against the values CloudWatch accepts, and `0` (keep forever) is rejected on purpose.

M1.5 then calls all three modules from `envs/dev`, passing outputs of one as inputs of the next, for example `module.vpc.private_subnet_ids` into the endpoints.

## Why it's built this way
- **Own KMS key, rotation on.** Flow logs reveal your network layout. M2.1 will add a shared `kms` module, and this can then take a key as input.
- **365-day default retention.** checkov rule `CKV_AWS_338` wants a year, and investigations often need old traffic. Storage is billed per GB-month, so scratch environments should pass something small. Even the drill stack uses the default, since a log group that lives ten minutes holds almost nothing and a skip would need a written reason.
- **CloudWatch Logs rather than S3.** Easier to search with no extra setup. S3 is cheaper at high volume and works with Athena; it could be added later.
- **Dev shares one NAT gateway** (ADR 0004): roughly a third of the cost, but egress is lost in every AZ if the NAT gateway's AZ fails. The variable `single_nat_gateway` flips it.
- **Tests assert on root outputs.** A root module can only see its children's outputs, not their resources, so `envs/dev` tests check output values.

## How it's tested
`vpc-flow-logs` unit tests (mock provider) check the names, the key policy's log group condition, the role's trust and permissions, the boundary, options and every validation. The Moto test applies `modules/vpc` and then the flow log on top and checks the flow log, log group, key and role are wired together. `envs/dev` has unit tests for the wiring (3 subnets per tier, one NAT gateway by default, three when `single_nat_gateway = false`, `az_count = 2`) and a Moto test that applies the whole root module and asserts 3 + 3 + 3 subnets, three private route tables and the NAT gateway counts. Moto delivers no flow records, so that traffic really lands in the log group is proven only by the live drill.

## Interview questions
<details><summary>1. What do VPC flow logs contain, and what don't they?</summary>

Per-flow metadata: addresses, ports, protocol, packets, bytes, start and end time and accept or reject. Not payloads, and not DNS answers or DHCP traffic to the VPC's own resolver.

</details>

<details><summary>2. How do you stop a KMS key meant for one log group being used for others?</summary>

A key policy condition on `kms:EncryptionContext:aws:logs:arn` for that log group's ARN, which CloudWatch Logs includes in every encryption call.

</details>

<details><summary>3. Why does the flow log role have a trust policy condition on <code>aws:SourceAccount</code>?</summary>

To prevent the confused deputy problem: without it, a flow log in another account could name your role and make the service write with your permissions.

</details>
