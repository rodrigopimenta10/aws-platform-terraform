## What it is, in plain terms
A **root module** is the folder where you run `terraform apply`. The folders under `modules/` are reusable
building blocks; a root module picks blocks, configures the **provider** (the plugin that talks to AWS, told
which **region**, a geographic cluster of data centers, to use) and says where **state** is kept. A **backend**
is that storage location. Each environment (`dev`, later `prod`) gets its own root module so its state and
mistakes stay separate.

## How it works
It calls `labels` and hands the resulting tags to the provider:

```hcl
provider "aws" {
  region = var.region
  default_tags { tags = module.labels.tags }
}
```

`default_tags` makes the provider add those tags to every taggable resource, so later modules do not repeat them.
The backend block is only a comment:

```hcl
# backend "s3" { bucket = "..." key = "envs/dev/terraform.tfstate" use_lockfile = true }
```

## Why it's built this way
- **Backend commented out:** a backend cannot use variables, and `terraform init` fails if the bucket does
  not exist yet. It is enabled on purpose after bootstrapping (README steps 1-5).
- **`environment` hard-coded to `dev`:** a wrong variable cannot turn this folder into `prod`.
- **No resources yet, so no cost.** Resources arrive from M1 onward.

## How it's tested
Mock-provider `plan` tests check default names and tags, that overrides flow into `labels` and the region, and
that a malformed region fails validation. I first tried `expect_failures = [module.labels.var.project]` to test
a bad project name, but Terraform only allows expecting failures from the root module's own checkable objects,
so that case stays covered in the `labels` tests. No Moto test, because there is nothing to apply; M1.5 adds one.

## Try it yourself (10-15 min)
Add a `validation` block to `var.project` in `envs/dev/variables.tf` (so a bad name fails with the root
module's own message), then add a `rejects_bad_project` run in `tests/unit.tftest.hcl` using
`expect_failures = [var.project]`. Check with `scripts/check.sh envs/dev`.

## Interview questions
<details><summary>1. Why can't a backend block use variables?</summary>

Terraform needs the backend before it evaluates anything else, including variables, because it must load
state first. Values are passed as literals or with `-backend-config`.

</details>

<details><summary>2. What does `default_tags` do and what is its limit?</summary>

It tags every taggable resource created through that provider. It cannot tag resources that do not support
tags, and tags that differ per resource still go on the resource.

</details>

<details><summary>3. Why one root module per environment instead of workspaces?</summary>

Separate folders give separate state, reviewable differences and no risk of applying to the wrong
environment because a workspace was left selected.

</details>
