# 2026-11-18: M2.4 Account baseline

**Built today:** an `account-baseline` module with three account-wide security defaults: EBS encryption by default, the S3 account-level public access block and an IAM password policy. It is added to the `m2` live-drill stack.

## Warm-up: two questions from earlier notes
<details><summary>1. A GitHub Actions job assumes your deploy role. Someone pushes a branch called <code>main-fix</code> and the job is refused. Why is that the right outcome? (from <a href="2026-11-16.md">2026-11-16</a>)</summary>

The role's trust policy compares the token's `sub` claim (which names the repository and the ref) against exactly the allowed values, such as `repo:<owner>/<repo>:ref:refs/heads/main`. `main-fix` is a different ref, so the comparison fails and AWS refuses to hand out credentials. The scoping to the repository and branch is what makes OIDC safe: any workflow in the world can obtain a GitHub token, but only yours matches the subject.

</details>

<details><summary>2. Your private subnets need one NAT gateway for the whole VPC to save money. What do you lose, and when is it acceptable? (from <a href="2026-11-12.md">2026-11-12</a>)</summary>

You lose availability: if the AZ holding the NAT gateway fails, private subnets in the other AZs lose outbound internet access, and traffic between AZs adds data charges. That is acceptable for dev and drills, where a few minutes of outage is cheap compared with about $32 a month per extra gateway; production usually runs one per AZ.

</details>

## What it is, in plain terms
An AWS **account** has settings that apply to everything inside it, rather than to one resource. Three matter early:

- **EBS** (Elastic Block Store) is the disk service behind EC2 instances and EKS nodes. **Encryption by default** makes every newly created volume encrypted, even when the person creating it forgot to ask. It is per **region**.
- **S3 Block Public Access** at the account level overrides every bucket's own settings and policies, including buckets created later. A bucket can no longer be made public by a mistaken ACL or policy.
- The **IAM password policy** sets the rules for IAM users' console passwords (length, character classes, expiry, reuse). This platform avoids IAM users, but a break-glass user would otherwise get AWS's weak default.

All three are **singletons**: an account (or account and region) has one of each. You create them once; there is nothing to name or tag.

## How it works
Each setting is one resource:

```hcl
resource "aws_s3_account_public_access_block" "this" {
  account_id              = data.aws_caller_identity.current.account_id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}
```

The four flags cover the two ways a bucket becomes public (ACLs and policies) and what happens to ones that already are. The default KMS key for EBS is optional:

```hcl
resource "aws_ebs_default_kms_key" "this" {
  count   = var.enable_ebs_encryption_by_default && var.ebs_default_kms_key_arn != null ? 1 : 0
  key_arn = var.ebs_default_kms_key_arn
}
```

Without it, new volumes use AWS's managed `aws/ebs` key. A `validation` block rejects a key alias at plan time, because the API wants a key ARN.

## Why it's built this way
- **No switch for the S3 block or password character classes.** These are guardrails, and a flag to turn them off would be used first.
- **One instance per account.** Two stacks managing the same singleton would undo each other on every apply.
- **Honest limits.** Turning on EBS default encryption does not encrypt existing volumes. Destroying the module resets settings to AWS's defaults; it does not restore what was there before.
- **Password length 14, expiry 90 days, 24 remembered.** The 14 follows the CIS AWS benchmark (an industry hardening checklist). Rotation every 90 days is debated, since forced rotation can lead to weaker passwords, so it is a variable.

## How it's tested
Unit tests (mock provider) check the secure defaults, that the key resource exists only when a key ARN is given and encryption is on, and each validation (alias instead of ARN, short password, reuse and age out of range). The Moto test applies the EBS and password policy resources. Moto **cannot** test the S3 account block here: the provider addresses the S3 Control API as `<account-id>.<endpoint>`, a hostname that cannot point at `127.0.0.1`. My first attempt failed with "no such host", so the Moto run uses `plan_options { target = ... }` to leave that resource out, and the README says so. That resource gets coverage from the unit tests and the live drill. I also had to pass `account_id` explicitly because the Moto provider skips the account lookup that normally fills it in.

## Live drill
The `m2` stack now applies the module and takes three more screenshots: the EC2 data-protection settings, the S3 account block settings and the IAM password policy. **Expected cost:** nothing, all three settings are free. **Watch out:** these are account-wide, so the drill's destroy resets them to AWS defaults; if your account had any of them already, it will lose them. Likeliest failure: the console text the screenshots wait for ("EBS encryption", "Block Public Access settings for this account", "Password policy"), which I could not check offline.

## Try it yourself (10-15 min)
Add a unit run to `modules/account-baseline` that sets `password_max_age_days = 0` and asserts the policy is still created with `max_password_age == 0` (0 means "never expires" in AWS). Check with `scripts/check.sh modules/account-baseline`, then commit it to `main`.

## Interview questions
<details><summary>1. Why enable S3 Block Public Access at the account level when each bucket can already block public access?</summary>

Per-bucket settings depend on everyone remembering. The account setting overrides all buckets, existing and future, so one mistaken ACL or policy cannot expose data.

</details>

<details><summary>2. You turn on EBS encryption by default. What does it not do?</summary>

It does not encrypt existing volumes or other regions. It applies only to volumes created afterwards, in the region where it was set. Existing volumes need a snapshot copied with encryption and a new volume from it.

</details>

<details><summary>3. Why is the IAM password policy still worth setting if you use SSO and roles?</summary>

Any IAM user that does exist (break-glass, legacy) falls back on AWS's weak default policy. Setting it is cheap and it is a standard benchmark check.

</details>
