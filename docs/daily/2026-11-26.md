## Warm-up: two questions from earlier notes
Answer these from memory before reading on.

<details><summary>1. Two teams share an AWS account and each runs a load balancer controller. How can one controller be allowed to delete load balancers without being able to delete the other team's? (from <a href="2026-11-24.md">2026-11-24</a>)</summary>

Scope the destructive actions by tag with a condition: the controller tags what it creates (for example with its cluster name), and the policy allows delete only where that tag is present on the resource. `Resource: "*"` is then acceptable for actions that cannot name a resource up front, because the condition does the narrowing.

</details>

<details><summary>2. A pipeline pushes image <code>app:1.4</code> twice with different contents. What happens against an ECR repository from our module, and why was it built that way? (from <a href="2026-11-19.md">2026-11-19</a>)</summary>

The second push is rejected, because tags are immutable. That way a tag always names one exact image, so a deployment, a scan result and a rollback all refer to the same bytes. A mutable tag lets a node pull different code under the same name.

</details>

## What it is, in plain terms
**GitOps** means the Git repository is the description of what runs in the cluster, and a program inside the cluster keeps the cluster matching it. **Argo CD** is that program. Its main objects:

- **Application:** one deployable thing (a Helm chart or a folder of manifests) plus where to put it. Argo CD compares it with the cluster and reports `Synced` or `OutOfSync`.
- **AppProject:** a fence around Applications. It limits which repositories they may read and which clusters and namespaces they may write to.
- **App-of-apps:** one *root* Application whose source folder contains only other Application manifests. Apply the root once and Argo CD creates the rest; adding an add-on later is a commit.

Argo CD itself must exist first, so it is installed once with Helm. That single step is the **bootstrap**.

## How it works
`bootstrap/root-app.yaml` points at the folder of children and turns on automatic sync:

```yaml
source:
  repoURL: https://github.com/rodrigopimenta10/aws-platform-terraform.git
  targetRevision: main
  path: platform/argocd/apps
syncPolicy:
  automated: {prune: true, selfHeal: true}
```

`prune` deletes cluster objects whose manifest left Git; `selfHeal` reverts hand edits. Each child has two **sources**: the upstream chart, and this repo, which only supplies the values file:

```yaml
sources:
  - repoURL: https://kubernetes-sigs.github.io/metrics-server/
    chart: metrics-server
    targetRevision: 3.12.2
    helm:
      valueFiles: [$values/platform/metrics-server/values.yaml]
  - repoURL: https://github.com/rodrigopimenta10/aws-platform-terraform.git
    targetRevision: main
    ref: values
```

`ref: values` names the second source, and `$values/...` reads a file from it. So the values files from yesterday are reused unchanged. The load balancer controller and external-dns Applications also pass `REPLACE_ME` parameters for the per-cluster inputs; those must be edited per cluster, which is deliberately loud.

## Why it's built this way
- **A separate AppProject** instead of `default`, which allows any repo and any namespace. A typo in an Application then cannot deploy outside `kube-system`, `external-dns` and `argocd`.
- **Chart versions are written twice** (the Application and `charts.env`), because Argo CD cannot read a shell file. Rather than trust discipline, `platform/tests/lint.sh` fails when they differ, when a values file is missing, or when a source is not allowed by the project.
- **Automated sync** is the point of GitOps but can surprise you: a hand-edit disappears. Fine for platform add-ons; a team new to it may want it off at first.
- **`REPLACE_ME` placeholders** over real values: cluster name, VPC id and zone are not for a public repo, and a wrong value should fail visibly.
- **Cost:** Argo CD runs about five small pods; on kind it costs nothing, on EKS it uses some node capacity.

## Interview questions
<details><summary>1. What problem does the app-of-apps pattern solve?</summary>

Applications are Kubernetes objects too, so something must create them. One root Application that points at a folder of Application manifests creates them all, and keeps them in sync. A new cluster needs one `kubectl apply`; a new add-on needs one commit.

</details>

<details><summary>2. What do <code>prune</code> and <code>selfHeal</code> do, and what is the risk?</summary>

`prune` deletes cluster resources whose manifests were removed from Git. `selfHeal` reverts changes made directly in the cluster. Together they make Git authoritative, but an accidental file deletion or an urgent manual hotfix is undone automatically, so teams often start with them off.

</details>

<details><summary>3. Why give the platform its own AppProject?</summary>

The default project allows any source and destination. A dedicated project limits which repositories an Application may read and which namespaces it may write, so a mistake or compromised repo has a smaller blast radius.

</details>
