## Warm-up: two questions from earlier notes

<details><summary>1. You turn on "EBS encryption by default" for a region on Monday. On Tuesday someone asks why a volume created last month is still unencrypted. What do you tell them? (from <a href="2026-11-18.md">2026-11-18</a>)</summary>

The setting only applies to volumes and snapshot copies created after it is switched on, and only in that region. Existing volumes are not changed. To encrypt one you snapshot it, copy the snapshot with encryption, and create a new volume from the copy.

</details>

<details><summary>2. A security group blocks an inbound connection to an instance. Will the VPC flow log show it? What about the instance's DNS lookups to the VPC resolver? (from <a href="2026-11-14.md">2026-11-14</a>)</summary>

Yes to the first: flow logs record rejected traffic as `REJECT` records, with addresses, ports and protocol (never the payload). No to the second: traffic to the VPC's own DNS resolver is not logged in flow logs, so DNS needs Route 53 resolver query logging.

</details>

## What it is, in plain terms
**Kubernetes** runs containers across many machines. It has a **control plane**: an **API server** (what `kubectl` talks to) and **etcd**, the database holding every object, such as Deployments and Secrets. **EKS** (Elastic Kubernetes Service) is AWS running that control plane for you, across several availability zones, for $0.10 an hour. You bring the **worker nodes**, which are the machines that run your containers (tomorrow's work).

A few terms:

- **Endpoint access.** The API server has a URL. It can be *private* (resolves to addresses inside your VPC, reachable only from there), *public* (reachable from the internet) or both.
- **Envelope encryption of Secrets.** Kubernetes Secrets are only base64-encoded in etcd. With a KMS key, EKS encrypts each Secret with a data key and the data key with your KMS key (see [2026-11-17](2026-11-17.md)).
- **Control-plane logs.** Five streams (`api`, `audit`, `authenticator`, `controllerManager`, `scheduler`) sent to CloudWatch Logs. `audit` records who did what to the cluster.
- **Access entries.** The modern way to say which IAM roles or users may use the Kubernetes API, and with what permissions. The older way was a ConfigMap named `aws-auth` edited inside the cluster.

## How it works
The cluster resource sets the safety-relevant choices directly:

```hcl
vpc_config {
  subnet_ids              = var.subnet_ids
  endpoint_private_access = true
  endpoint_public_access  = var.endpoint_public_access
  public_access_cidrs     = var.endpoint_public_access ? var.public_access_cidrs : null
}

access_config {
  authentication_mode                         = "API"
  bootstrap_cluster_creator_admin_permissions = false
}

encryption_config {
  resources = ["secrets"]
  provider { key_arn = var.kms_key_arn }
}
```

`authentication_mode = "API"` means only access entries grant access. `bootstrap_cluster_creator_admin_permissions = false` removes a surprise: by default whoever creates the cluster gets an invisible `cluster-admin`, which appears nowhere in code.

The control plane needs an IAM role that the EKS service assumes. It goes through [`modules/iam-role`](../../modules/iam-role/), so it must carry the permissions boundary, and gets AWS's `AmazonEKSClusterPolicy`. The log group is created by the module, named `/aws/eks/<cluster>/cluster` (the only name EKS writes to), with retention and a KMS key. Access entries become `aws_eks_access_entry` plus an `aws_eks_access_policy_association`, scoped to the whole cluster or to listed namespaces:

```hcl
access_scope {
  type       = length(each.value.namespaces) == 0 ? "cluster" : "namespace"
  namespaces = length(each.value.namespaces) == 0 ? null : each.value.namespaces
}
```

## Why it's built this way
- **Private by default, public with CIDRs.** A `validation` block rejects `0.0.0.0/0`, and a `precondition` rejects "public on, no CIDRs". The cost of private-only is that you need a path into the VPC (VPN, bastion, a CI runner inside) to run `kubectl`.
- **No creator admin means an empty `access_entries` gives an unusable cluster.** That is on purpose. The plan shows who can administer the cluster. The drill stack passes none, because nobody needs `kubectl` during a drill.
- **The module owns the log group.** If it did not, EKS would create one with no expiry and no key. Retention defaults to 365 days because checkov (`CKV_AWS_338`) wants a year, rather than skipping the check.
- **`audit` can't be turned off.** A validation requires it. Everything else about logging is adjustable.
- **Version pinned by variable.** AWS upgrades the control plane only when `kubernetes_version` changes, and never skips a minor version.
- **Cost.** The control plane is about $73 a month even with no nodes. That is why the drill destroys it within minutes.

## How it's tested
- **Unit tests (mock provider, plan):** private-by-default endpoint, Secrets encryption, five log types, `API` mode with no creator admin, log group name, retention and key, public opt-in, access entries and their scope, the boundary on the role, and eight `expect_failures` runs for the validations and the public-endpoint precondition.
- **Moto test (apply):** applies [`modules/kms`](../../modules/kms/), then the cluster, role and log group, and reads back what Moto stored. Two Moto limits: it has **no access-entry API** (CreateAccessEntry returns 404), so access entries are covered by unit tests only; and it does not load **AWS-managed IAM policies** unless started with `MOTO_IAM_LOAD_MANAGED_POLICIES`, which `scripts/check.sh` doesn't set. I overrode the one policy attachment in that test rather than change the shared script. A side effect: no test can see the attachment at all, because a root module cannot read a child module's resources. The README says so.
- A test can't `expect_failures` on a resource inside a child module either, so the "role without a boundary is rejected" test stays in [`modules/iam-role`](../../modules/iam-role/), where it already exists.

## Interview questions

<details><summary>1. Why make the EKS API endpoint private, and what do you give up?</summary>

The API server controls the whole cluster, so not exposing it to the internet removes a large attack surface. You give up convenience: `kubectl` and CI must run inside the VPC or over a VPN, bastion or similar. If a public endpoint is needed, restrict it to known CIDRs.

</details>

<details><summary>2. Why use EKS access entries instead of the aws-auth ConfigMap?</summary>

Access entries are managed through the AWS API, so Terraform and CloudTrail can see them, and a mistake can't lock you out of the in-cluster ConfigMap that gates access. They also map straight to AWS-managed access policies and can be limited to namespaces.

</details>

<details><summary>3. What does enabling secrets encryption with KMS protect against, and what does it not?</summary>

It protects Secrets at rest in etcd (and backups): reading the raw storage doesn't reveal them, and every key use is auditable. It does not protect anyone who can call the Kubernetes API with permission to read Secrets, because the API decrypts for them. RBAC and least-privilege access still decide who can read Secrets.

</details>
