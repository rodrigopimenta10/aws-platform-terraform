## What it is, in plain terms
A pod that reads from S3 or a queue needs AWS credentials. Long-lived keys in a Kubernetes Secret leak and never expire. The node's own role would be shared by every pod on the node. **Pod Identity** gives each workload its own role, delivered as temporary credentials:

- A **service account** is the identity a pod runs as inside Kubernetes (like a username for pods). A **namespace** is a folder that groups Kubernetes objects.
- An **association** is an EKS record: "pods running as service account `orders-api` in namespace `orders` of cluster X get role R".
- The **agent** (the `eks-pod-identity-agent` add-on from yesterday) runs on every node. When the AWS SDK in a pod asks for credentials, the agent asks EKS to assume the role for that pod and hands back one-hour credentials.

The older approach, **IRSA** (IAM Roles for Service Accounts), does the same with OIDC tokens and an identity provider per cluster. ADR 0005 compares them.

## How it works
The role trusts the EKS service itself, not a cluster-specific identity provider:

```hcl
Principal = { Service = "pods.eks.amazonaws.com" }
Action    = ["sts:AssumeRole", "sts:TagSession"]
Condition = {
  StringEquals = { "aws:SourceAccount" = data.aws_caller_identity.current.account_id }
  ArnEquals    = { "aws:SourceArn" = "arn:...:eks:*:<account>:cluster/${var.cluster_name}" }
}
```

The two conditions are a **confused-deputy** guard. The deputy is the EKS service, which acts for many customers. Without them, someone in another account could ask the service to assume your role for their cluster. With them, it works only when the request comes from your account and your cluster. (`*` stands in for the region: roles are global, and the cluster name and account are enough.) `sts:TagSession` lets EKS stamp the session with the cluster, namespace and service account.

The role is made through `iam-role`, so the boundary is mandatory, and the permission policy is inline:

```hcl
resource "aws_iam_role_policy" "this" {
  count  = var.policy_json == null ? 0 : 1
  name   = "${var.name}-inline"
  role   = module.role.role_name
  policy = var.policy_json
}
```

Then the association, the part that links the role to the workload:

```hcl
resource "aws_eks_pod_identity_association" "this" {
  cluster_name    = var.cluster_name
  namespace       = var.namespace
  service_account = var.service_account
  role_arn        = module.role.role_arn
}
```

## Why it's built this way
- **Pod Identity, not IRSA** (ADR 0005). One fixed trust statement for every cluster, no OIDC provider, and moving a workload is an association edit. IRSA stays the answer for Fargate and old SDKs.
- **Exact service account names.** No wildcards: a wildcard would hand the role to every pod in the namespace.
- **Inline policy.** It belongs to one workload. A separate managed policy would have an ARN unknown until apply, which a `for_each` over attachments cannot take at plan time.
- **Where the test for "no boundary" lives.** In `iam-role`: a test cannot expect a failure inside a child module's resource.
- **Cost:** free. The drill's example role can only describe the `api` ECR repository.

## How it's tested
- **Unit tests (mock provider, plan):** the association's cluster, namespace, service account and tags; the trust policy's service, account, cluster and `sts:TagSession` (read through a `trust_policy` output); the boundary; no inline policy by default and one when `policy_json` is set; and `expect_failures` for a capital-letter name, a bad cluster name, a bad namespace, a `*` service account, non-JSON policy and a malformed boundary ARN.
- **No Moto test.** Moto does not implement the Pod Identity API, so the README says so and the live drill covers it. The `m3` stack test also checks the example role's name, which the console link depends on.
- A first draft of the trust-policy test tried to reach into the child module's role. Tests only see outputs, so the policy became a local with its own output.

## Interview questions

<details><summary>1. How does a pod get AWS credentials with Pod Identity, step by step?</summary>

An association ties a service account to a role. A pod running as that service account makes an SDK call; the SDK asks the node-local agent for credentials; the agent asks EKS, which assumes the role for that pod and returns temporary credentials. The role trusts `pods.eks.amazonaws.com`.

</details>

<details><summary>2. When would you still pick IRSA over Pod Identity?</summary>

On Fargate (no node to run the agent), on EKS Anywhere or self-managed Kubernetes outside EKS, or with an SDK too old to support the credential endpoint. Otherwise Pod Identity is simpler: no OIDC provider and the same trust policy everywhere.

</details>

<details><summary>3. What is the confused-deputy problem and how do the two conditions in the trust policy address it?</summary>

A service that acts on behalf of many customers can be tricked into using its authority for the wrong one. `aws:SourceAccount` and `aws:SourceArn` make the role usable only when the request comes from your account and your cluster, so another customer cannot name your role in their association.

</details>
