## What it is, in plain terms
**KMS** (Key Management Service) holds encryption keys for you. You never see the key material: services send data to KMS (or ask for a data key) and KMS does the cryptography. A **customer-managed key** is a key you create and whose access policy you write; the alternative is a key AWS owns invisibly. The payoff is control and audit: every use shows up in **CloudTrail** (AWS's API activity log), you can disable the key to cut off access to all data under it, and reading encrypted data takes permission on the data *and* on the key.

A **key policy** is the access document attached to the key itself. Most AWS resources are controlled by IAM policies alone, but a KMS key is the exception: with no key policy, nobody can use it. An **alias** is a friendly name (`alias/platform-live-logs`) that points at a key. **Key rotation** means AWS periodically creates fresh key material; old material is kept so earlier data still decrypts.

## How it works
The policy is built from a list of statements, and only the ones you ask for are included:

```hcl
statements = concat(
  [ { Sid = "EnableIAMPolicies", Principal = { AWS = "arn:...:root" }, Action = "kms:*", ... } ],
  length(var.key_administrator_arns) == 0 ? [] : [ { Sid = "KeyAdministratorsManageButCannotUse", ... } ],
  length(var.key_user_arns) == 0 ? [] : [ { Sid = "KeyUsersEncryptAndDecrypt", ... } ],
  [ for k, g in var.service_grants : merge({ ... }, <condition if any>) ],
)
```

Administrators get actions such as `kms:ScheduleKeyDeletion`, `kms:Put*` and `kms:Disable*` but nothing that encrypts or decrypts. Users get `kms:Decrypt`, `kms:Encrypt` and `kms:GenerateDataKey*` but nothing that changes the key.

A service grant can carry an **encryption context**: labelled data that the calling service attaches to every KMS request, and that KMS records in CloudTrail. The module turns it into a condition:

```hcl
Condition = { StringEquals = { "kms:EncryptionContext:aws:logs:arn" = "arn:aws:logs:...:log-group:/aws/platform-live/app" } }
```

CloudWatch Logs puts the log group's ARN in that context, so the key can encrypt this log group and no other.

## Why it's built this way
- **Admins cannot read data.** If the person who can edit the key policy could also decrypt, one compromised admin credential would expose everything. Splitting the duties costs one extra statement.
- **The root statement stays.** `Principal: root` with `kms:*` looks alarming, but it means "IAM policies in this account may grant access". Without it, deleting the one admin role would orphan the key. checkov's wildcard rules (`CKV_AWS_109`, `111`, `356`) are skipped inline with that reason; in a key policy `Resource: "*"` can only mean this key.
- **Rotation can't be switched off**, only tuned (90 to 2560 days). AWS rotates yearly by default.
- **One key per purpose.** Each key costs about $1 a month, so separate keys for logs, ECR and state are cheap, and each has its own policy and its own blast radius.
- **Keys can't be deleted instantly.** Scheduling deletion starts a 7 to 30 day wait, because deleting a key makes everything under it unreadable for ever. Default 30; the drill uses 7.
- **`vpc-flow-logs` keeps its own key for now.** Switching it over would change a module that works and has been drilled. It is a good follow-up once the key module has been drilled.

## How it's tested
Unit tests (mock provider) assert the defaults (rotation on, alias and `Name` tag from `labels`, a policy of just the root statement), that the administrator statement contains no data-use action and the user statement no management action, the encryption context condition, and each input validation (bad purpose, non-IAM ARNs, bad service principal, rotation or deletion window out of range, vague description). The Moto test applies the module with all three kinds of principal and checks key, alias and outputs. **Moto stores the policy but does not enforce it**, so whether a service really can or can't use the key is shown only by the drill.

## Interview questions
<details><summary>1. Why does a KMS key policy usually include a statement for the account root?</summary>

It lets IAM policies in the account grant access to the key. Without it, only principals named in the key policy have access, and removing the last of them leaves a key nobody can administer without contacting AWS Support.

</details>

<details><summary>2. How do you stop CloudWatch Logs using a key for log groups other than yours?</summary>

Add a condition on `kms:EncryptionContext:aws:logs:arn` equal to the log group's ARN, because the service includes it in every request to KMS.

</details>

<details><summary>3. What happens to encrypted data if you schedule the key for deletion and the wait ends?</summary>

It becomes permanently unreadable, because the key material is gone. That is why the wait is 7 to 30 days, and why you can cancel deletion during it.

</details>
