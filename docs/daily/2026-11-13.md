## Warm-up: two questions from earlier notes
<details><summary>1. Your team turns off NAT in a dev VPC to save money, and a pod in a private subnet can no longer pull a public image. Which two designs restore access, and what does each cost you? (from <a href="2026-11-12.md">2026-11-12</a>)</summary>

Turn NAT back on (single or per AZ), which bills hourly plus per GB. Or give the subnet a route to the internet some other way, which defeats the private tier. Today's answer for AWS-only traffic is endpoints: no NAT, but you pay per endpoint per AZ-hour and only AWS services are reachable.

</details>

<details><summary>2. A colleague says "versioning already protects the state bucket, so the KMS key is redundant." What does the key add? (from <a href="2026-11-10.md">2026-11-10</a>)</summary>

Versioning is an undo history, not access control. With a customer-managed key, reading the state needs both S3 and KMS permission, and every use of the key is logged in CloudTrail.

</details>

## What it is, in plain terms
A private subnet has no route to the internet, so by default nothing in it can reach AWS's own APIs either (those live at public addresses). A **VPC endpoint** is a private doorway to an AWS service. There are two kinds:

- A **gateway endpoint** (only S3 and DynamoDB) is a route-table entry: traffic for S3 is sent straight to S3 over AWS's network. It is free and has no network interface.
- An **interface endpoint** (**ENI**, elastic network interface, is a virtual network card) puts a network interface with a private IP into your subnets. A **private DNS** override makes the normal hostname, such as `sts.us-east-1.amazonaws.com`, resolve to that private IP inside the VPC, so code needs no changes. It bills per endpoint per AZ-hour plus per GB.

A **security group** is a stateful firewall attached to a network interface: it lists what may connect in, and replies are allowed back automatically.

## How it works
The four interface endpoints come from one map, so adding a fifth is one line:

```hcl
interface_services = {
  ecr_api = "ecr.api"
  ecr_dkr = "ecr.dkr"
  sts     = "sts"
  logs    = "logs"
}
```

`aws_vpc_endpoint.interface` and `aws_security_group.interface` both use `for_each` over the chosen keys, so each endpoint is wired to its own group:

```hcl
security_group_ids  = [aws_security_group.interface[each.key].id]
private_dns_enabled = var.private_dns_enabled
```

The ingress rules are a cross product of endpoints and allowed CIDRs (`setproduct`), each TCP 443 only. The S3 gateway endpoint takes `route_table_ids`, so the private and isolated route tables each get a route to S3.

## Why it's built this way
- **ECR needs three doors.** `ecr.api` handles login and metadata, `ecr.dkr` speaks the registry protocol, and image layers are stored in S3. Without the S3 endpoint a pull hangs after authenticating.
- **One security group per endpoint** so reachability is auditable per service. No egress rules: an endpoint never starts connections.
- **`0.0.0.0/0` is rejected** by a validation. Endpoints are for traffic from inside the VPC.
- **Cost is the trade-off.** About $0.01 per endpoint per AZ-hour: four endpoints in three AZs is roughly $87 a month before data. They pay off when NAT per-GB charges for AWS traffic are bigger, or when you need private-only networking. The S3 gateway endpoint is free either way.
- **One checkov skip**, `CKV2_AWS_5`, a false positive: the groups are attached through `each.key` indexing that checkov cannot follow. The reason is inline.

## How it's tested
Mock-provider `plan` tests check service names, one security group and one rule per endpoint, subsets, disabling S3, the policy option and every validation rule. The Moto test applies `modules/vpc` and then the endpoints on top and checks the gateway is attached to three route tables, each interface endpoint spans both private subnets, security groups are distinct, and the rules are TCP 443 from the VPC CIDR. A security group's own `ingress` and `egress` attributes stay empty when rules are separate resources, so the tests inspect the rule resources. Moto does not resolve private DNS or carry traffic, so that is proven only by the live drill.

## Interview questions
<details><summary>1. Gateway versus interface endpoint?</summary>

A gateway endpoint is a route-table entry for S3 or DynamoDB, free and with no network interface. An interface endpoint is a network interface with a private IP and private DNS for most other services, billed per AZ-hour and per GB.

</details>

<details><summary>2. A private-subnet node cannot pull an image from ECR even though the ECR endpoints exist. What do you check?</summary>

The S3 gateway endpoint and its route table association (layers come from S3), private DNS enabled on both ECR endpoints, the endpoint security group allowing 443 from the node's CIDR, and DNS support and hostnames enabled on the VPC.

</details>

<details><summary>3. When are interface endpoints cheaper than NAT?</summary>

When lots of AWS-service traffic would otherwise pass through NAT at its per-GB charge. With little traffic the hourly endpoint charges cost more than they save, so endpoints are then chosen for private-only networking and security.

</details>
