# 2026-11-10: M0.2 Remote state (`modules/state-backend`)

**Built today:** a `state-backend` module (S3 bucket + KMS key) for storing Terraform state, plus ADR 0003 on why locking uses S3 itself instead of DynamoDB.
**Files:** [modules/state-backend](../../modules/state-backend/), [unit tests](../../modules/state-backend/tests/unit.tftest.hcl), [Moto test](../../modules/state-backend/tests/integration.tftest.hcl), [ADR 0003](../adr/0003-s3-native-state-locking.md).

## What it is, in plain terms
Terraform's **state file** is its memory of which real resources it created. Kept on one laptop, it is
easy to lose and impossible to share, so teams store it in a **remote backend**. On AWS that is usually
**S3** (Simple Storage Service, object storage; a **bucket** is a named container of files). State can
contain secrets and cannot be regenerated, so the bucket must be private, encrypted, versioned and locked.

**KMS** (Key Management Service) holds encryption keys. A **customer-managed key** is one you own and
control with a policy, as opposed to a key AWS manages invisibly. A **bucket policy** is a JSON document
attached to the bucket that allows or denies requests.

## How it works
The module calls `labels` for names and tags, then creates the key and the bucket with its settings as
separate resources (the AWS provider v6 splits bucket settings out of `aws_s3_bucket`).

```hcl
bucket_name = "${module.labels.names["tfstate"]}-${data.aws_caller_identity.current.account_id}-${data.aws_region.current.region}"
```

S3 bucket names are unique across **all** AWS accounts worldwide, so the account ID and region are
appended: `platform-dev-tfstate-123456789012-us-east-1`.

```hcl
Condition = { Bool = { "aws:SecureTransport" = "false" } }
```

This sits in a `Deny` statement, so any request made over plain HTTP is refused. An explicit `Deny` always
beats any `Allow`.

## Why it's built this way
- **Versioning** gives an undo history for state; a **lifecycle rule** deletes old versions after 90 days
  (minimum 7 enforced by a `validation`) so history does not grow forever.
- **SSE-KMS with our own key and rotation:** reading state needs S3 *and* KMS permission, and key use
  shows up in CloudTrail. Costs about $1/month for the key.
- **Public access block + `BucketOwnerEnforced`:** four switches that make public exposure impossible, and
  ACLs (an older permission system) are turned off so IAM is the only authority.
- **S3 native locking (`use_lockfile`)** rather than DynamoDB: see ADR 0003. One fewer table to create.
- **`force_destroy = false` by default:** a stray `terraform destroy` cannot delete your state.
- **checkov skips with reasons:** access logging, cross-region replication and event notifications are
  skipped inline (they would need a second bucket or double the cost). The KMS key policy's `Resource = "*"`
  is required: in a key policy it means "this key".
- **Bootstrapping catch-22:** the bucket that stores state needs state itself. The first apply uses local
  state, then you migrate. M0.3 documents it.

## How it's tested
- **Unit (mock provider, plan):** bucket name, versioning, KMS algorithm and rotation, all four public
  access settings, the TLS-deny policy JSON, lifecycle days, standard tags, and `expect_failures` for bad
  retention and KMS window values. To make the policy testable at plan time, its ARNs are built from the
  bucket *name* (known early) instead of the bucket's `arn` attribute (unknown until apply).
- **Moto (apply):** one run creates everything and asserts versioning, key rotation, public access block
  and `backend_config`.
- **Moto limitation I hit:** I first had `newer_noncurrent_versions` ("always keep the last N versions") in
  the lifecycle rule. Moto accepts it but does not return it when read back, and the AWS provider polls
  until the read matches, so apply hung for 3 minutes and failed. I removed the option rather than skip
  the Moto test. Moto also does not enforce the TLS deny, so that is covered by the unit test only.

## Try it yourself (10-15 min)
Add a `kms_key_arn` variable (default `null`) so callers can bring their own key, and create the module's
key only when it is null (`count`). Add a unit test for both cases. Check with
`scripts/check.sh modules/state-backend`.

## Interview questions
<details><summary>1. Why is state locking needed and how does S3 do it without DynamoDB?</summary>

Two concurrent applies would read the same state and the later write would overwrite the first. With
`use_lockfile`, Terraform writes a `.tflock` object using an S3 conditional write that fails if the object
already exists, so only one run holds the lock.

</details>

<details><summary>2. Why a customer-managed KMS key instead of the default S3 encryption?</summary>

You control the key policy, can rotate and audit it, and can revoke access. Reading the state then needs
both S3 and KMS permissions, which gives a second layer of access control and a CloudTrail record.

</details>

<details><summary>3. You applied a bad change and state is corrupted. How do you recover?</summary>

Because versioning is on, list the object's versions, download the last good one (or restore it as the
current version), and run `terraform plan` to confirm it matches reality. That is why the lifecycle rule
keeps versions for 90 days instead of deleting them quickly.

</details>
