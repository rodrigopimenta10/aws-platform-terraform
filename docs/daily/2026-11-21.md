<details><summary>1. A teammate pushes <code>v1.4</code> to your ECR repository, finds a bug, fixes it and pushes <code>v1.4</code> again. What happens in a mutable repository, what happens in an immutable one, and which would you want when you debug a production incident? (from <a href="2026-11-19.md">2026-11-19</a>)</summary>

In a mutable repository the second push silently moves the `v1.4` label to the new image, so a host that pulled earlier and a host that pulls now run different code under the same tag. In an immutable one the second push is rejected, so the teammate must publish `v1.5`. For an incident you want immutable: the tag in a deployment manifest then names exactly one image, so you can say what was running.

</details>

<details><summary>2. A flow log delivers to CloudWatch through an IAM role the flow-log service assumes. Without an <code>aws:SourceAccount</code> condition in that role's trust policy, what attack becomes possible? (from <a href="2026-11-14.md">2026-11-14</a>)</summary>

The confused deputy problem. The service is the "deputy" that holds permissions in your account. Without the condition, someone in another account can create a flow log that names your role and make the service write with your role's permissions. The condition ties the role to flow logs from your own account.

</details>

## What it is, in plain terms
An EKS cluster's control plane (yesterday) only stores what you want to run. The **worker nodes** are the EC2 instances (virtual machines) that actually run your containers. Each node runs the **kubelet**, the agent that takes instructions from the API server, and a container runtime. A **managed node group** is a set of nodes that EKS creates, joins to the cluster, drains before replacing and updates for you. Behind it EKS runs an **Auto Scaling group**, AWS's "keep this many instances running" service.

Terms used today:

- **Launch template.** A saved recipe for an EC2 instance: disk, metadata settings, tags. Node groups can be built from one.
- **IMDS (instance metadata service).** Every EC2 instance can read facts about itself, including its IAM role's temporary credentials, from `169.254.169.254`, an address that only the instance can reach. **IMDSv1** answers any plain GET request, so a bug that lets an attacker make your app fetch a URL (SSRF) can leak the credentials. **IMDSv2** first needs a session token obtained with a PUT request, which that kind of bug usually cannot send.
- **Hop limit.** How many network hops the IMDS answer may travel. Pods sit one hop further than the node's own processes, so a limit of 1 hides the node's credentials from pods.
- **Spot instances.** Spare EC2 capacity at a steep discount that AWS can take back with a two-minute warning. Good for work that tolerates interruption.
- **Label and taint.** A *label* is a key-value tag on a node that pods can ask for (`nodeSelector`). A *taint* repels pods unless they carry a matching *toleration*. Labels attract, taints keep out.
- **Node role.** The IAM role the instance itself uses to join the cluster and pull images. It is not the role of your application.

## How it works
The shared role trusts EC2 and gets three AWS-managed policies, through [`modules/iam-role`](../../modules/iam-role/) so the permissions boundary is mandatory:

```hcl
managed_policy_arns = concat([
  "arn:${data.aws_partition.current.partition}:iam::aws:policy/AmazonEKSWorkerNodePolicy",
  "arn:${data.aws_partition.current.partition}:iam::aws:policy/AmazonEKS_CNI_Policy",
  "arn:${data.aws_partition.current.partition}:iam::aws:policy/AmazonEC2ContainerRegistryPullOnly",
], var.additional_node_policy_arns)
```

Worker node lets the kubelet describe the cluster, CNI lets the VPC networking plugin assign addresses to pods, and `PullOnly` lets nodes pull images but never push them (older guides use `ReadOnly`, which allows more).

Each group gets its own launch template, built with `for_each` over the `node_groups` map:

```hcl
metadata_options {
  http_endpoint               = "enabled"
  http_tokens                 = "required" # IMDSv2 only
  http_put_response_hop_limit = var.metadata_hop_limit
}

block_device_mappings {
  device_name = "/dev/xvda"
  ebs { volume_size = each.value.disk_size_gib, volume_type = "gp3", encrypted = true, kms_key_id = var.ebs_kms_key_arn, delete_on_termination = true }
}
```

The template names no image, so EKS selects the optimized Amazon Linux 2023 image for the group's `ami_type` and cluster version. The node group then points at the template:

```hcl
launch_template {
  id      = aws_launch_template.this[each.key].id
  version = aws_launch_template.this[each.key].latest_version
}
labels = merge(each.value.labels, { "node-group" = each.key })
dynamic "taint" { for_each = each.value.taints ... }
```

`ignore_changes = [scaling_config[0].desired_size]` stops Terraform undoing what an autoscaler decides later.

## Why it's built this way
- **IMDSv2 required, hop limit 1.** This is the standard fix for credential theft through SSRF. The trade-off: software that predates Pod Identity and reads node credentials breaks, and the variable lets you raise the limit to 2 knowingly. M3.5 moves workloads to Pod Identity so they stop needing it.
- **Spot needs two or more instance types.** One type is one capacity pool, so a single reclaim can remove every node. A validation rejects it rather than documenting it.
- **No image in the launch template.** It keeps EKS in charge of the image, which is what makes "update the node group" work. You give up custom AMIs.
- **One shared role.** All groups need identical permissions. Splitting roles later is easy; maintaining several identical ones is not.
- **`PullOnly` and no extra policies by default.** A node role is reachable from every pod on the node when the hop limit allows it, so it should be as small as possible.
- **Cost.** Nodes are the real bill: a `t3.medium` is about $30 a month on demand, spot is often 60 to 70 percent less. Scale-to-zero spot groups cost nothing while empty.

## Interview questions

<details><summary>1. Why require IMDSv2 on worker nodes, and why a hop limit of 1?</summary>

IMDSv1 returns the node's IAM credentials to any simple request, so an SSRF bug in any pod can steal them. IMDSv2 requires a token from a PUT request. A hop limit of 1 additionally means traffic from a pod, which passes through one more network hop, can't reach the metadata service, so pods can't borrow the node role. Pods that need AWS access should get their own role through Pod Identity or IRSA.

</details>

<details><summary>2. When would you pick spot nodes for a node group, and how do you keep the wrong workloads off them?</summary>

For fault-tolerant, restartable work such as batch jobs, CI runners or stateless replicas behind enough on-demand capacity. Spread across several instance types so one reclaimed pool doesn't remove everything. Taint the spot nodes so only pods that tolerate the taint (and say so with a `nodeSelector` on a label) are scheduled there. Databases or single replicas should stay on on-demand nodes.

</details>

<details><summary>3. What is the difference between a label and a taint?</summary>

A label is descriptive: pods select nodes by it (`nodeSelector`, node affinity). A taint is a restriction: pods are kept off the node unless they tolerate it. You often use both: the taint keeps general workloads out, the label lets the intended workload find the node.

</details>
