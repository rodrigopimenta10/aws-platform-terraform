Nobody can, until an access entry is added. By default the creator gets an invisible `cluster-admin` that appears nowhere in code. Turning it off means every administrator is listed in the plan, at the price of an unusable cluster until you add one.

</details>

<details><summary>2. A GitHub job's token says it came from a pull request, but your deploy role's trust policy only lists the <code>main</code> branch. What happens, and which claim does the check use? (from <a href="2026-11-16.md">2026-11-16</a>)</summary>

AWS refuses to hand out credentials. The trust policy compares the token's `sub` (subject) claim, which names the repository and context, for example `repo:org/repo:pull_request`, against the exact subjects listed. A pull request's subject is not `...:ref:refs/heads/main`, so it does not match, which keeps untrusted code away from the deploy role.

</details>

## What it is, in plain terms
A Kubernetes cluster needs a few helper programs before it is useful, and an **EKS add-on** is one of those programs packaged by AWS. EKS tests each add-on version against each Kubernetes version and can install or upgrade it with one API call instead of you applying YAML by hand. Today's five:

- **vpc-cni** (the VPC Container Network Interface plug-in). Gives every pod a real IP address from your VPC. It runs as a **DaemonSet**, Kubernetes' "one copy on every node" object.
- **coredns.** Cluster DNS, so a pod can call `my-service.my-namespace.svc`. It needs nodes to run on, so without nodes it sits *Degraded*.
- **kube-proxy.** Programs each node's network rules so a Service address leads to a real pod.
- **eks-pod-identity-agent.** Runs on each node and hands pods temporary credentials for their own IAM role. **Pod Identity** is the newer way to give a pod AWS permissions. The older one is **IRSA** (IAM Roles for Service Accounts), which needs an OIDC identity provider per cluster. M3.5 compares them properly.
- **aws-ebs-csi-driver.** Lets pods use **EBS** (Elastic Block Store, AWS's network disks) as storage. **CSI** (Container Storage Interface) is Kubernetes' plug-in standard for storage. The driver calls the EC2 API to create and attach disks, so it needs an IAM role of its own.

A new cluster already runs default copies of the first three that EKS installed itself. Nobody chose their versions and nothing in code mentions them. Declaring them as resources hands them to Terraform.

## How it works
One `aws_eks_addon` per map entry:

```hcl
resource "aws_eks_addon" "this" {
  for_each = var.addons

  cluster_name                = var.cluster_name
  addon_name                  = each.key
  addon_version               = each.value.version
  resolve_conflicts_on_create = "OVERWRITE"
  resolve_conflicts_on_update = each.value.resolve_conflicts_on_update
```

`OVERWRITE` matters because the default copies exist already. It tells EKS: where the cluster's settings and yours differ, yours win. `PRESERVE` keeps hand edits instead and is opt-in.

The version has no default, and a validation accepts only an exact build:

```hcl
condition = alltrue([for k, a in var.addons : can(regex("^v[0-9]+\\.[0-9]+\\.[0-9]+-eksbuild\\.[0-9]+$", a.version))])
```

For the EBS driver the module builds the role, trusting the EKS pods service instead of an OIDC provider:

```hcl
Principal = { Service = "pods.eks.amazonaws.com" }
Action    = ["sts:AssumeRole", "sts:TagSession"]
Condition = { StringEquals = { "aws:SourceAccount" = data.aws_caller_identity.current.account_id } }
```

and links the role to the driver's service account inside the add-on resource:

```hcl
pod_identity_association {
  service_account = "ebs-csi-controller-sa"
  role_arn        = each.value.pod_identity_role_arn != null ? each.value.pod_identity_role_arn : module.ebs_csi_role[0].role_arn
}
```

A `precondition` stops the plan if the driver is requested without `eks-pod-identity-agent`: the driver would start and have no credentials.

## Why it's built this way
- **Pinned, no `latest`.** Add-on versions are tied to the Kubernetes minor version and a floating default would change on an ordinary `apply`. The cost is hand-editing numbers at upgrade time, which is the review point.
- **Pod Identity, not IRSA.** One fixed trust statement for every cluster, no OIDC provider to create, and the role-to-service-account link lives in EKS. The trade-off is that it needs the agent add-on and a recent platform version.
- **`aws:SourceAccount` on the trust policy.** The same confused-deputy guard as the flow-log role (see the warm-up in the 2026-11-21 note): the service acts for your account only.
- **The role goes through `iam-role`.** The boundary is mandatory. A caller can bring its own role with `pod_identity_role_arn`.
- **Volumes with a customer key are not covered.** The AWS policy handles `aws/ebs` only. A customer-managed key needs a KMS statement on the role. I left that as a follow-up rather than add an inline policy to the shared `iam-role` module today.
- **Cost.** The add-ons are free; their pods use node capacity.

## How it's tested
- **Unit tests (mock provider, plan):** pinned versions and cluster name, `OVERWRITE` defaults, tags, no role unless the EBS driver is present, boundary on the created role, the Pod Identity association, a supplied role replacing the created one, configuration values passed through, the driver refusing to plan without the agent, and seven `expect_failures` runs (unpinned and partial versions, empty map, bad conflict policy, non-JSON configuration, bad role ARN, bad cluster name).
- **No Moto test.** Moto does not implement `CreateAddon`, so there is nothing to apply against. The README says so, and the live drill covers it.
- Two things went wrong on the way. A test cannot `expect_failures` on a resource inside a child module, so "no boundary is rejected" stays in `modules/iam-role`. And in the drill stack a `depends_on` on the whole module made its data sources wait for apply, which broke the plan; the stack now carries the "nodes exist first" dependency through a `terraform_data` value instead.

## Interview questions

<details><summary>1. Why manage EKS add-ons in Terraform instead of using the ones a new cluster comes with?</summary>

The default copies work but nobody chose their versions, and they upgrade only when someone remembers. As resources, the version is in code, an upgrade is a reviewed change, and `OVERWRITE` makes the cluster match the code. It also lets you set options such as replica counts or resource limits.

</details>

<details><summary>2. How does the EBS CSI driver get permission to create disks, and why not give the node role that permission?</summary>

Through Pod Identity: a role trusted by `pods.eks.amazonaws.com` is associated with the driver's service account, and only that pod gets its credentials. Putting the permission on the node role would hand it to every pod on every node, so one compromised pod could create and delete volumes.

</details>

<details><summary>3. What does <code>resolve_conflicts_on_update = "OVERWRITE"</code> change, and when would you choose <code>PRESERVE</code>?</summary>

If someone edited the add-on's settings in the cluster, `OVERWRITE` replaces those edits with the configuration in code, so code stays the source of truth. `PRESERVE` keeps the hand edits, which is a stopgap while you move a custom setting into `configuration_values`. It hides drift, so it is not a good default.

</details>
