## What it is, in plain terms
A cluster is only useful once something runs on it, so this is the smallest realistic **workload**: a web server that answers `/` and `/healthz`. The pieces:

- **Container image:** a packaged filesystem plus a start command. A **Dockerfile** is the recipe. A **multi-stage** build uses one image to compile and a second, tiny one to run, copying only the result across.
- **Deployment:** tells Kubernetes "keep two copies (pods) of this running" and how to replace them during an update.
- **Service:** a stable address in front of changing pods.
- **Ingress:** a rule for traffic from outside the cluster. With the load balancer controller from M4.1, an Ingress becomes an **Application Load Balancer (ALB)**, AWS's HTTP-level load balancer.
- **PodDisruptionBudget (PDB):** a limit on *voluntary* evictions. Draining a node for maintenance asks Kubernetes to evict its pods; the PDB says how many must stay up.
- **NetworkPolicy:** a firewall rule between pods.

## How it works
The Dockerfile has two stages. The build stage makes a static binary; the final stage is distroless (an image with no shell or package manager) running as UID 65532:

```dockerfile
FROM golang:1.24-alpine AS build
RUN CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o /out/sample-app .

FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/sample-app /sample-app
USER 65532:65532
```

The Deployment adds defence in depth even if someone swaps the image: `runAsNonRoot`, a read-only root filesystem, all Linux capabilities dropped, no ServiceAccount token mounted, and `maxUnavailable: 0` so a new pod must be ready before an old one stops.

The PDB and the Deployment must agree: with 2 replicas, `minAvailable: 1` lets a drain evict one pod at a time.

```yaml
spec:
  minAvailable: 1
  selector:
    matchLabels: {app.kubernetes.io/name: sample-app}
```

The Ingress uses `target-type: ip`, so the ALB sends traffic to pod IPs and the health check hits `/healthz`. The server handles SIGTERM by finishing in-flight requests (`srv.Shutdown`), so rollouts and drains drop nothing.

## Why it's built this way
- **Distroless, non-root, multi-stage** over a fat base image: a smaller image has fewer vulnerabilities to scan and fewer tools for an attacker.
- **Plain manifests, not Helm or Kustomize:** five short files are easier to read and the lint can check them. Argo CD can point at the folder as-is.
- **`minAvailable` below `replicas`:** if they were equal, no node could ever be drained and cluster upgrades would hang. That is a classic outage, so the lint checks it.
- **Two checkov skips**, both with reasons in the code: `CKV_K8S_43` (image digest) because the image is a `REPLACE_ME` placeholder, and `CKV_DOCKER_2` (HEALTHCHECK) because Kubernetes probes replace it and distroless has no shell. I did not skip the NetworkPolicy and pull-policy findings; I fixed them.
- **NetworkPolicy blocks all egress:** the app calls nothing. It only has effect if the CNI enforces policies, which the vpc-cni add-on must be configured to do.
- **Cost:** two 50m CPU / 32Mi pods are negligible; the ALB (about $0.0225 an hour plus usage) is the only AWS charge, and only when deployed for real.

## How it's tested
- `go test ./...` in `platform/sample-app`: `/healthz` returns 200 `ok`, `/` shows the version, unknown paths return 404.
- `platform/tests/lint.sh` now also checks that every selector and label matches across the Deployment, Service, PDB and NetworkPolicy, that the Service targets the container's named port, that the Ingress points at the Service, that the PDB leaves room to drain, that the pod is non-root with a read-only filesystem, and that the Dockerfile is multi-stage and ends as non-root. I confirmed it fails when `minAvailable` is set to 2.
- `checkov -d platform/sample-app --framework kubernetes,dockerfile`: 0 failed, 1 skipped for each framework as above. Neither this lint nor the Kubernetes scan is run by `scripts/check.sh` (it is outside what I may edit freely), so run them by hand; `scripts/check.sh` itself printed ALL CHECKS PASSED.
- **Not run:** `docker build` and any deploy. The sandbox has no Docker daemon or cluster. The Dockerfile and manifests are checked statically only.

## Interview questions
<details><summary>1. What does a PodDisruptionBudget protect against, and what does it not?</summary>

It limits voluntary disruptions such as node drains, autoscaler consolidation and upgrades, by refusing evictions that would leave fewer than `minAvailable` pods. It does not stop involuntary ones (a node crashing, an out-of-memory kill), which is why replicas should also be spread across zones.

</details>

<details><summary>2. Why run a container as non-root with a read-only filesystem?</summary>

If the application is compromised, the attacker has the same rights as the process. Without root they cannot install tools or change system files; with a read-only root filesystem they cannot write a payload to disk.

</details>

<details><summary>3. What is the difference between a readiness and a liveness probe?</summary>

Readiness decides whether the pod receives traffic (failing removes it from the Service and the ALB target group). Liveness decides whether the container is restarted. Using liveness for slow dependencies causes restart loops; readiness is the right tool there.

</details>
