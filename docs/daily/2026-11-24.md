## What it is, in plain terms
Two pieces of software run as pods but manage AWS resources:

- The **AWS Load Balancer Controller** watches Kubernetes `Ingress` and `Service` objects. An *Ingress* is a Kubernetes rule that says "send traffic for this hostname to that service". The controller turns it into an **Application Load Balancer** (ALB, HTTP-aware) or **Network Load Balancer** (NLB, plain TCP), with **target groups** (the pods or nodes behind it), **listeners** (ports) and **security groups** (virtual firewalls).
- **Karpenter** looks for pods that cannot be scheduled for lack of room, then launches **EC2** instances (virtual machines) of a fitting size and joins them to the cluster. When they are empty it terminates them.

Both need an IAM **policy**, a JSON document listing the API calls allowed. They are long, and mistakes are costly: too narrow and the controller silently does nothing; too broad and a compromised controller pod can delete every load balancer or launch machines wearing an admin role.

## How it works
The module makes two `aws_iam_policy` resources and exposes each document as an output too. It makes no role: a policy grants nothing until a role carries it, and the role (with its permissions boundary) comes from `eks-pod-identity`.

**Scoping by tag.** The load balancer controller tags everything it creates. Mutating statements only match resources with that tag:

```hcl
lb_tag_cluster_present = { Null = { "aws:ResourceTag/elbv2.k8s.aws/cluster" = "false" } }
```

`Null ... = "false"` reads as "the tag is *not* null", that is, present. So `DeleteLoadBalancer` works on its own load balancers and fails on the one a teammate made by hand. Karpenter does the same with `kubernetes.io/cluster/<name> = owned`, and its `TerminateInstances` statement requires that tag on the instance.

**`iam:PassRole` pinned.** To launch an instance with a role, a caller needs `iam:PassRole` for that role:

```hcl
Action    = ["iam:PassRole"]
Resource  = var.karpenter_node_role_arn
Condition = { StringEquals = { "iam:PassedToService" = ["ec2.amazonaws.com"] } }
```

If this were `Resource = "*"`, Karpenter could start an instance wearing an administrator role, log in, and use it. That is **privilege escalation**, so the statement names one role and one service.

**Region pinned.** Karpenter's EC2 resource ARNs contain `var.region`, and its Describe calls carry `aws:RequestedRegion`.

**Where `*` is unavoidable.** `Describe*` calls have no resource-level permissions in IAM, so their `Resource` must be `*`. checkov flags that; each policy carries four skips with the reason written inline.

## Why it's built this way
- **Written out, not fetched.** Both documents follow the projects' reference policies, as `jsonencode` locals. They are reviewable in a diff and testable offline. The cost is that I wrote them from my knowledge of the upstream policies, with no internet check available here: **compare them with the upstream files when you adopt a controller version.** The drill proves IAM accepts them, not that they are complete for every feature.
- **Policies separate from roles.** Which service account gets the policy is a per-cluster decision. Making the role here would also drag the boundary into a module that doesn't need it.
- **The 6,144-character limit.** A managed policy can't exceed it; whitespace doesn't count, and `jsonencode` has none. A unit test fails before IAM does.
- **A trap I hit and documented.** `iam-role` attaches managed policies with `for_each` over their ARNs. A policy created in the same apply has an unknown ARN at plan time, so Terraform refuses. The drill stack passes the document as `policy_json` instead; the README explains both ways round. I did not change `iam-role` today (outside this item).

## How it's tested
Unit tests (mock provider): names and tags; both documents under the size limit; every load balancer mutation conditioned on the cluster tag; no wildcard actions; Karpenter's delete and read statements tied to the cluster and region; `PassRole` names one role and only EC2; the queue statement appears only when a queue is given; policies can be switched off; a precondition when Karpenter has no node role; and validation failures for region, cluster name and both ARNs. The Moto test applies both policies; Moto parses the JSON, so it catches malformed documents, but it doesn't evaluate permissions, so *what* is allowed is asserted by reading the document.

## Interview questions

<details><summary>1. Why must iam:PassRole be restricted, and how is it here?</summary>

Launching an instance with a role requires PassRole. If it allows any role, the caller can launch a machine with an admin role and use that, escalating its own privileges. Here it names one node role and the condition `iam:PassedToService = ec2.amazonaws.com`.

</details>

<details><summary>2. How can a controller be allowed to delete load balancers without being able to delete anyone else's?</summary>

By conditioning the delete on a tag. The controller tags what it creates, and the statement only matches resources carrying `elbv2.k8s.aws/cluster`, so hand-made load balancers are outside its reach.

</details>

<details><summary>3. Why does "Resource": "*" appear in the policies, and when is it acceptable?</summary>

Some actions, such as the EC2 `Describe*` calls, don't support resource-level permissions, so `*` is the only valid value. It is acceptable for read-only calls like these, with the reason written down; mutating actions should name resources or be limited by conditions.

</details>
