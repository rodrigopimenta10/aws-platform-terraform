## What it is, in plain terms
A CI pipeline that deploys to AWS needs credentials. The old way is an **access key** (a permanent ID and secret) pasted into GitHub's secrets. If it leaks it works from anywhere until someone notices.

**OIDC** (OpenID Connect) removes the stored secret. When a GitHub Actions job runs, GitHub can sign a small **token** that says which repository, branch or environment the job belongs to. You tell AWS to trust GitHub's signature by creating an **identity provider** in **IAM** (Identity and Access Management, AWS's users, roles and permissions service). The job sends the token to **STS** (Security Token Service) and receives credentials that expire in an hour. A **role** is an identity with permissions that anyone allowed by its **trust policy** can temporarily become. The trust policy only decides who may become the role; a separate permissions policy decides what the role can do.

## How it works
The trust policy is where the security lives:

```hcl
Principal = { Federated = local.provider_arn }
Action    = "sts:AssumeRoleWithWebIdentity"
Condition = {
  StringEquals = {
    "${local.host}:aud" = "sts.amazonaws.com"
    "${local.host}:sub" = local.subjects
  }
}
```

`aud` (audience) says the token was meant for AWS. `sub` (subject) says where the job runs. The module turns each allowed context into one exact subject:

```hcl
[for b in var.allowed_branches : "repo:${local.repo_part}:ref:refs/heads/${b}"]
```

so `main` in `example-org/example-repo` becomes `repo:example-org/example-repo:ref:refs/heads/main`. Environments and pull requests are added the same way. With `github_owner_id` and `github_repository_id` set, the subject carries numeric IDs, the form the drill repository's tokens use.

Because the account can have only one provider per URL, `create_provider = false` makes the module trust the existing one. Its ARN is built from the documented format, so the policy is known at plan time either way.

## Why it's built this way
- **`StringEquals`, never wildcards.** `repo:owner/*` or `refs/heads/*` would admit every repository you own, or every branch anyone can push. The `validation` blocks reject `*` too.
- **Pull requests are off by default.** A pull request from a fork runs workflow code its author wrote, so it must not get deploy permissions.
- **No permissions in the module.** Callers pass `managed_policy_arns`; otherwise the module would become an admin role by default. A `permissions_boundary` (a cap on what a role can ever do) can be added too.
- **Refuses an empty trust list.** A `precondition` fails the plan if no branch, environment or PR is allowed, since that role could never be assumed.
- **No thumbprint.** AWS validates GitHub's certificate against its own trusted authorities, so the old `thumbprint_list` is gone.
- **One-hour sessions** by default: a deploy takes minutes, and a leaked token dies sooner.

## How it's tested
Unit tests (mock provider) assert the default trust policy (web identity, GitHub provider, STS audience, exactly `main`), the exact subjects for branches, environments, pull requests and ID form, `create_provider = false`, boundary and policy attachment, the empty-list precondition, and each validation (wildcards, one ID without the other, non-numeric IDs, session range, bad policy ARN). The Moto test applies provider and role and checks the stored trust policy. **Moto doesn't enforce trust policies and has no AWS-managed policies like `ReadOnlyAccess`**, so attachment is unit-tested only and real assumption is shown by the drill. One test first failed because the mock reports `client_id_list` as a set, which can't be compared with `==` to a list; I use `contains` instead.

## Interview questions
<details><summary>1. Why is OIDC safer than an access key in GitHub secrets?</summary>

Credentials are issued per job and expire within an hour, there is nothing permanent to leak or rotate, and AWS accepts only tokens GitHub signed for the repository, branch or environment the trust policy names.

</details>

<details><summary>2. What is the difference between a role's trust policy and its permissions policy?</summary>

The trust policy says who may assume the role; the permissions policies say what the role can do once assumed. A tight trust policy with admin permissions, or the reverse, is still a weakness.

</details>

<details><summary>3. Why match the token subject with exact strings instead of <code>repo:my-org/*</code>?</summary>

A wildcard trusts every current and future repository in the org, including ones with weaker review, and `refs/heads/*` trusts any branch someone can push. Exact subjects keep the blast radius to the one place that is meant to deploy.

</details>
