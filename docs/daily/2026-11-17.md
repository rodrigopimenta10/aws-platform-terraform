## Warm-up: two questions from earlier notes
<details><summary>1. A role has an IAM policy allowing <code>kms:*</code> on everything, yet it still gets AccessDenied using your new customer-managed key. What do you check first, and why does KMS behave differently from S3 here? (from <a href="2026-11-15.md">2026-11-15</a>)</summary>

The **key policy**. Every KMS key has its own resource policy, and IAM policies alone are not enough: the key policy must allow the caller directly, or contain the statement that delegates to IAM (an Allow for the account root principal). Without that delegation, identity policies are ignored for that key.

</details>

<details><summary>2. A colleague says a subnet is private because its name contains "private". Its route table has <code>0.0.0.0/0</code> pointing at an internet gateway. Who is right? (from <a href="2026-11-11.md">2026-11-11</a>)</summary>

The route table decides, not the name. A route to an internet gateway makes the subnet public (instances with public IPs are reachable). A subnet is private when it has no such route.

</details>

## What it is, in plain terms
An IAM **role** is an identity that a person, service or CI job can temporarily become. It gets permissions from **policies** attached to it. Normally whoever attaches policies decides what the role can do, and a role with `AdministratorAccess` can do everything.

A **permissions boundary** is a second policy attached to the role as a ceiling. The role's effective permissions are the **intersection** of its own policies and the boundary: an action works only if both allow it. The boundary grants nothing on its own. This matters because roles get created by automation and by many people. The boundary is a guarantee that holds whatever someone attaches later.

The hole in that idea: if a role is allowed to create *other* roles, it can create one with no boundary, assume it and escape. So the boundary has to forbid creating roles without it.

## How it works
The boundary document has an allow-list of services and then explicit Denies. An explicit **Deny** beats any Allow in any policy, so Denies are how escalation is closed:

```hcl
{
  Sid      = "DenyRolesWithoutThisBoundary"
  Effect   = "Deny"
  Action   = ["iam:CreateRole", "iam:PutRolePermissionsBoundary"]
  Resource = "*"
  Condition = {
    StringNotEquals = { "iam:PermissionsBoundary" = local.policy_arn }
  }
}
```

Reading it: refuse `CreateRole` unless the request names *this* boundary. The same pattern guards the other doors: no removing a boundary from a role, no editing or deleting the boundary policy, no IAM users or access keys, and no requests outside the allowed regions (global services like IAM and STS are exempt, since they have no regional endpoint).

The policy mentions its own ARN, so the module builds the ARN from the name, account and partition instead of reading it from the resource. Reading it back would be a dependency cycle.

The role module is the Terraform side of the same rule:

```hcl
lifecycle {
  precondition {
    condition     = var.permissions_boundary != null
    error_message = "Role ${local.name} has no permissions boundary. ..."
  }
}
```

A **precondition** is a check Terraform runs at plan time, before any change reaches AWS, and it fails the plan with your message.

## Why it's built this way
- **Two layers.** The precondition gives a friendly error at `terraform plan`. The boundary's own Deny is enforced by AWS for any role creation, including one made by hand or by someone else's code. Neither alone is enough: Terraform can't stop a bare `aws_iam_role`, and an AWS-side denial only appears at apply time.
- **Allow-list of services.** A new AWS service stays out of reach until someone lists it.
- **`iam` is not in the default allow-list.** A role that manages IAM is privileged. If a caller adds it, the Denies still stop users, keys and unbounded roles.
- **No escape-hatch variable** to skip the boundary. It would be used first under pressure.
- **Honest limits.** `aws:RequestedRegion` only says which endpoint was called, so the region Deny is a guardrail, not a data-residency guarantee. The boundary also doesn't restrict *resource-based* policies in the same account, which can grant access by themselves.
- **checkov skips** (CKV_AWS_288/289/290/355) each carry a reason: a boundary's `Allow` on `Resource = "*"` is its normal shape because it is only a ceiling.

## How it's tested
Unit tests (mock provider) check the allow-list, each Deny, the self-referencing condition value, the region exemptions and every validation. In `iam-role`, a run with `permissions_boundary = null` uses `expect_failures = [aws_iam_role.this]`, so the test **passes only if the plan is rejected**. Moto applies the policy and the role and checks what was stored. **Moto doesn't evaluate boundaries**, so the boundary's real effect on a role is shown only by the live drill. Two hiccups: comparing a list from a policy document with `==` failed (a tuple isn't equal to a list in Terraform's type system), so I compare `jsonencode(...)` of both; and the new lock files needed all four platform checksums, so I copied them from `github-oidc`, which has the same provider version and constraint, because the registry is blocked in this environment.

## Interview questions
<details><summary>1. What is a permissions boundary and how is it different from a role's policy?</summary>

A boundary is a policy that sets the maximum permissions of a role or user. Effective permissions are the intersection of the identity policies and the boundary. It never grants access by itself, whereas an identity policy does.

</details>

<details><summary>2. How do you stop a role that can create roles from escalating its own privileges?</summary>

Deny `iam:CreateRole` and `iam:PutRolePermissionsBoundary` unless the request carries the required boundary (condition `iam:PermissionsBoundary`), and deny removing boundaries and editing the boundary policy. The role then can only create roles that are equally capped.

</details>

<details><summary>3. Why check for a boundary in Terraform when IAM already denies it?</summary>

Feedback speed and clarity. A `precondition` fails at plan time with a message naming the role, instead of a generic AccessDenied at apply time, and it works before anything is created. The IAM Deny remains the real enforcement.

</details>
